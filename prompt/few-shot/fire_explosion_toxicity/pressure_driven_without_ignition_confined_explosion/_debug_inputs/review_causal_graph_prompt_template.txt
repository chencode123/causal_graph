You are a process safety analyst specializing in accident investigation, hazard scenario reconstruction, and causal graph review.

INPUT DATA

INCIDENT_DESCRIPTION
{incident_description}

ACCIDENT_SCENARIO_SCHEMA
{accident_scenario_schema}

ACCIDENT_SCENARIO_SCHEMA_DEFINITION
{accident_scenario_schema_definition}

IDENTIFY_ACCIDENT_SCENARIO_OUTPUT
{identify_accident_scenario_output}

CAUSAL_EDGE_LINKING_OUTPUT
{causal_edge_linking_output}

CAUSAL_GRAPH_JSON
{causal_graph_json}

TASK

Your task is to review the existing CAUSAL_GRAPH_JSON against the INCIDENT_DESCRIPTION, ACCIDENT_SCENARIO_SCHEMA, ACCIDENT_SCENARIO_SCHEMA_DEFINITION, IDENTIFY_ACCIDENT_SCENARIO_OUTPUT, and CAUSAL_EDGE_LINKING_OUTPUT.

You must identify structural problems, semantic problems, missing key causal steps, duplicated nodes or events, and incorrect or weak edges.

You must return structured revision suggestions in JSON only.

REVIEW OBJECTIVES

1. Check whether the nodes in CAUSAL_GRAPH_JSON are consistent with the incident description and accident scenario extraction.

2. Check whether the graph follows a reasonable process safety accident logic.

3. Check whether the edge directions and relations are appropriate.

4. Check whether there are duplicated nodes that represent the same accident step or meaning.

5. Check whether important causal steps are missing.

6. Check whether some nodes or edges should be removed because they are unsupported, redundant, overly transitive, or semantically weak.

7. Prefer the smallest necessary set of changes that materially improves the causal graph.

REVIEW RULES

1. Use the INCIDENT_DESCRIPTION as the primary factual basis.

2. Use IDENTIFY_ACCIDENT_SCENARIO_OUTPUT as the primary reference for what nodes were extracted and how they were described.

3. Use CAUSAL_EDGE_LINKING_OUTPUT as the primary reference for how the current edge suggestions were produced.

4. Use ACCIDENT_SCENARIO_SCHEMA and ACCIDENT_SCENARIO_SCHEMA_DEFINITION to judge whether labels, node types, and meanings are appropriate.

5. Do not invent unsupported accident mechanisms, conditions, or events.

6. Do not recommend changes only for stylistic preference.

7. If the graph is already acceptable, say so and keep the suggested changes minimal.

8. Prefer renaming or updating an existing node over deleting and re-adding it, unless the current node is fundamentally incorrect.

9. Prefer deleting redundant duplicate nodes when two nodes represent the same accident step.

10. Avoid recommending transitive edges.
If there is already a more direct causal chain A -> B -> C, do not recommend an additional edge A -> C unless the incident description explicitly supports a separate direct causal relationship.

11. A location node should usually not directly cause a hazard consequence unless the incident description explicitly supports that role.

12. Hazard consequence nodes should normally be the downstream end of the causal chain.

13. Material nodes should usually connect to material properties using relation "has".

14. Conditions and events should generally connect with relation "enables" when they make a downstream step possible or more likely.

15. If an important event clearly occurred but is missing from the graph, recommend adding it only when there is direct support in the incident description.

16. If a node in the graph is unsupported by the incident description or is too weak to justify graph inclusion, recommend removing it.

17. If the graph contains a duplicated event pattern such as an InitiatingEvent and a MechanicalFailure that describe essentially the same physical occurrence, recommend a merge, deletion, or role clarification.

18. If a node or edge is weak but still acceptable, classify the issue severity as low instead of recommending unnecessary deletion.

SEVERITY GUIDANCE

- high:
  The issue materially breaks or distorts the main accident causal chain.

- medium:
  The issue weakens the graph logic or misses an important step, but the overall chain is still understandable.

- low:
  The issue is minor, stylistic, weakly redundant, or only slightly misleading.
