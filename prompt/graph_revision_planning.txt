TASK

Your task is to convert GRAPH_DIAGNOSIS_OUTPUT into a minimal, evidence-grounded revision plan for the current CAUSAL_GRAPH_JSON.

You must use GRAPH_DIAGNOSIS_OUTPUT as the primary problem list.
Use GRAPH_DIAGNOSIS_OUTPUT.issues_summary as the only formal source of revision-triggering
issues.
Use GRAPH_DIAGNOSIS_OUTPUT.case_assessment.main_problems only as a high-level summary, not
as an independent basis for proposing new revisions.
Use GRAPH_DIAGNOSIS_OUTPUT.issue_type_checks only as a consistency check, not as an
independent source of revisions.
Do not re-diagnose the graph from scratch unless a diagnosis item is clearly inconsistent
with the provided evidence.

PLANNING RULES

  1. Use the INCIDENT_DESCRIPTION as the primary factual basis.

  2. Use GRAPH_DIAGNOSIS_OUTPUT as the primary reference for what should be fixed.

  3. Every recommended change must explicitly map to at least one issue already listed in
     GRAPH_DIAGNOSIS_OUTPUT. Do not propose a change that cannot be traced to a diagnosis
     issue.

  4. Prefer the smallest necessary set of changes that materially improves the causal graph.

  5. Prefer renaming or updating an existing node over deleting and re-adding it, unless the
     current node is fundamentally incorrect.

  6. Prefer connecting a weakly connected node to existing nodes before recommending a new
     node.

  7. Only recommend a new node when the missing causal role cannot be adequately represented
     by the existing nodes.

  8. Delete a node only when it is unsupported, redundant, or cannot be validly connected
     with evidence support.

  9. Avoid recommending transitive edges. If there is already a more direct causal chain A
     -> B -> C, do not recommend an additional edge A -> C unless the incident description
     explicitly supports a separate direct causal relationship.

  10. Except HazardConsequence nodes, every retained node should have at least one outgoing
     edge.

  11. Every retained Condition node should have both at least one incoming edge and at least
      one outgoing edge.

  12. For each link inside node_additions, provide link-specific explanation and evidence
      for that exact edge.

  13. If no material changes are needed, return empty change lists.

  13a. If GRAPH_DIAGNOSIS_OUTPUT contains no material supported issues, do not invent
      revisions. Return empty change lists and keep issues_summary empty.

  14. Treat shortcut_edge as an edge that bypasses a necessary or strongly supported
      intermediate causal step and makes the graph overly direct. If the evidence supports a
      more local chain A -> B -> C, then a direct edge A -> C should normally be removed or
      replaced with the more local chain unless the incident description explicitly supports
      a separate direct relationship from A to C.

  15. Add a new node only when the missing causal role is explicitly or strongly supported
      by the evidence and cannot be adequately represented by any existing node.

  16. If the necessary causal semantics are already present in existing nodes, prefer
      adding, deleting, or updating edges rather than creating a new node.

  17. If an edge is diagnosed as a shortcut_edge and a more local supported chain can be
      represented using existing or newly justified nodes, prefer deleting that shortcut
      edge.

  18. Before recommending any edge addition, check whether the proposed new edge would
      bypass a necessary or strongly supported intermediate local step. If it would create a
      shortcut edge, do not recommend adding that edge. Prefer preserving, restoring, or
      introducing the more local chain instead.

  19. Delete a node only when it is unsupported, redundant, or cannot be repaired into a
      valid causal role with evidence-supported connections.

  20. Prefer this intervention order when several options are plausible: edge update or edge
      add or edge delete, then node update, then node addition, then node deletion.

  21. Any newly added node should have a clear upstream and/or downstream causal role
      justified by the evidence. Do not create a new node that remains weakly connected or
      structurally invalid after the proposed revision.

  22. Do not add a new HazardConsequence node. Treat the hazard consequence inventory as
      fixed by CAUSAL_GRAPH_JSON.

  23. If GRAPH_DIAGNOSIS_OUTPUT appears to imply a missing or changed hazard consequence,
      convert that into node updates, edge updates, edge additions, edge deletions, or no
      change. Do not emit a HazardConsequence entry in node_additions.

  24. Do not introduce any new problem statement that is not already covered by
      GRAPH_DIAGNOSIS_OUTPUT. Planning may refine how to fix a diagnosis item, but it must
      not expand the problem list beyond the diagnosed issues.

  25. Do not propose a revision from issue_type_checks alone unless the same problem is
      also represented in issues_summary.

  26. Do not propose a revision for any issue_type marked not_present in
      GRAPH_DIAGNOSIS_OUTPUT.issue_type_checks.

  27. For every recommended node or edge change, explicitly state which diagnosis issue or
      issues it addresses.

  28. Use stable diagnosis issue references based on the order of
      GRAPH_DIAGNOSIS_OUTPUT.issues_summary:
      the first issue is "issue_1", the second is "issue_2", and so on.
      Use these refs consistently in issues_summary and in every change entry.

OUTPUT REQUIREMENTS

If GRAPH_DIAGNOSIS_OUTPUT reports no material supported issue, return a no-change plan:

  - keep node_updates, node_additions, node_deletions empty
  - keep edge_additions, edge_deletions, edge_updates empty
  - keep issues_summary empty
  - summarize briefly that no evidence-grounded revision is needed

Do not propose placeholder revisions just to make the plan look complete.

NODE UPDATE STATE FORMAT

For node_updates, current_state and suggested_state must be JSON objects, not free-form
strings.

For change_type = rename:
  - current_state should include the current name
  - suggested_state should include only the new name

For change_type = relabel:
  - current_state should include the current label
  - suggested_state should include only the new label

For change_type = retype:
  - current_state should include the current node_type
  - suggested_state should include only the new node_type

Use this format:

{{
  "current_state": {{
    "name": "string",
    "label": "string",
    "node_type": "string"
  }},
  "suggested_state": {{
    "name": "string",
    "label": "string",
    "node_type": "string"
  }}
}}

Only populate the field relevant to the change_type. Leave unrelated fields omitted.

For rename, never write node display strings such as
`Ev3 = IntermediateEvent: "New event name"` inside suggested_state.name.
Use only the plain replacement name:

{{
  "change_type": "rename",
  "current_state": {{
    "name": "Mixer motor started with solid explosive in pot 5"
  }},
  "suggested_state": {{
