TASK

Based on the INCIDENT_DESCRIPTION, the IDENTIFIED_HAZARD_CONSEQUENCE, and the CAUSAL_NARRATIVE_EXTRACTION, 
extract accident scenario elements that can explain how the identified hazard consequence occurs, 
and populate the SCHEMA.
You must strictly follow the provided SCHEMA and SCHEMA_DEFINITION.
The extracted nodes should collectively form a coherent accident progression leading to the hazard consequence.

Your task is to identify the key elements of the accident scenario including:

EXTRACTION RULES

1. Use the incident description as the primary source of information.

2. The hazard_consequence must copy the node provided in IDENTIFIED_HAZARD_CONSEQUENCE.
 
3. Evidence must be a short quote copied directly from the incident description whenever possible.

4. Do not invent or fabricate evidence.

A node may be supported by combining consistent statements from the text,
as long as at least one representative quote is provided.

5. If information is not available in the incident description or reliable sources, return "Not specified".

6. When determining the hazardous material, select the material that participates 
in the causal chain leading to the hazard consequence, particularly the material 
involved in the MechanicalFailure or InitiatingEvent.

Do not select materials that only appear as a result of the accident 
(e.g., generated gases, combustion products, or released debris).

7. For source, only use values allowed by the SCHEMA.

8. The initiating event should represent the earliest abnormal condition that begins the accident sequence.

9. The mechanical failure should represent the equipment failure that directly leads to the loss of containment or material release.

10. Release type should describe whether the release occurred suddenly (instant) or over time (continuous).

11. Ignition timing should reflect whether ignition occurred immediately after release or after some delay.

12. Confinement level should reflect the physical surroundings of the release location.

13. Dispersion presence indicates whether the released material dispersed as a vapor or gas cloud prior to ignition or harmful exposure.

14. Only populate scenario elements that actually occurred in the incident and are supported by the IDENTIFIED_HAZARD_CONSEQUENCE.

14a. The CAUSAL_NARRATIVE_EXTRACTION represents the primary causal interpretation 
of the accident progression.

Use it to guide the selection of nodes and ensure that the extracted elements 
are consistent with the causal chain.

However, all nodes must still be grounded in the INCIDENT_DESCRIPTION 
and supported by evidence.

15. Do not add events, intermediate conditions, or mechanism components 
only because they are commonly associated with the selected hazard consequence.

However, if the incident description or analysis section provides 
case-specific evidence of underlying physical mechanisms, 
these mechanisms may be represented when they help explain the accident progression.

16. Do not generate a generic hazard template. Generate only the accident scenario that was actually realized in this incident.

17. If ignition clearly occurred but the exact ignition source is not identified in the incident description, create an IgnitionSource event with the name "Unknown ignition source" instead of "Not specified".

18. If a mechanical failure clearly occurred but the exact failed component or exact failure mode is not identified in the incident description, create a MechanicalFailure event with the name "Unknown mechanical failure" instead of "Not specified".

19. Use "Not specified" for IgnitionSource or MechanicalFailure only when the report does not provide enough support to identify whether that event should be represented at all.

20. If the incident description presents a tightly connected upstream operational or physical process that directly leads to the first abnormal event, the InitiatingEvent name may summarize that connected process in one concise event name.

21. Do not merge multiple distinct downstream events, failure events, ignition events, or hazard consequences into the InitiatingEvent name. Only combine closely connected precursor steps that jointly define the same initiating mechanism.

22. For example, if stop-start transfer pumping caused turbulence and bubbling, which directly caused rapid static charge accumulation, these closely connected steps may be summarized in one InitiatingEvent. However, later mechanical failure or ignition steps should remain separate events.

23. Event decomposition principle: each event node should represent one local causal role only. Do not let one event node simultaneously represent an operational action, a physical release, an ignition step, and a downstream accident consequence.

24. If the incident text explicitly describes an operational or human action and a resulting physical process step, prefer representing them as separate event nodes rather than merging them into one node.

25. If the incident text explicitly distinguishes release, transport or dispersion, ignition, flame propagation or flashback, and final consequence, do not collapse those stages into one event node.

26. Only merge steps when they are tightly coupled and jointly define the same local mechanism. Do not merge across different causal stages.

27. Condition extraction principle: create condition nodes only when the condition has an independent reusable causal role in the graph. Do not extract purely descriptive or redundant states as condition nodes.

28. When directly supported by the incident description, prefer stable extraction of key causal conditions such as Phase, Combustibility, ReleaseType, Confinement, and Dispersion.

29. Do not use a condition node as a substitute for a clearly described event. If the text says something happened, represent that local happening as an event node.

Source rules

If the information is derived from the incident report,
set source to "incident_description".

If the information cannot be determined, use "Not specified".

OUTPUT REQUIREMENTS

Return a JSON object that strictly follows the structure defined in SCHEMA.

The output must:

• Use the exact field names defined in the SCHEMA
• Use only the allowed values specified in the SCHEMA
• Include evidence quotes whenever required  
• Use "Not specified" if the information cannot be determined

Do not include explanations or additional text outside the JSON structure.
