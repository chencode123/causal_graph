TASK

Your task is to diagnose problems in the existing CAUSAL_GRAPH_JSON.

DIAGNOSIS RULES

[Core grounding]

    1. Use the INCIDENT_DESCRIPTION as the primary factual basis.

    2. Use CAUSAL_NARRATIVE_EXTRACTION_OUTPUT as the primary reference for the intended
       accident progression and key intermediate causal steps.

    3. Use ACCIDENT_SCENARIO_SCHEMA and ACCIDENT_SCENARIO_SCHEMA_DEFINITION to judge whether
       labels, node types, and meanings are appropriate.

    4. Use CAUSAL_NODE_ISSUE_DEFINITION to judge whether node-related issue types are
       being applied correctly.

    5. Use CAUSAL_EDGE_SCHEMA_DEFINITION to judge whether edge relations, edge directions,
       and edge patterns are semantically valid.

    6. Use CAUSAL_EDGE_ISSUE_DEFINITION to judge whether edge-related issue types are
       being applied correctly.

    7. Use CAUSAL_ISSUE_OUTPUT_DEFINITION as the authoritative guide for shared
       diagnosis-style output structure.

    8. Diagnose node-level problems before edge-level problems whenever both are
       plausible explanations for the same structural defect.

    9. When assessing edge-level problems, evaluate them in this order:
       (1) missing_local_link,
       (2) wrong_relation,
       (3) unsupported_edge,
       (4) shortcut_edge.
       Diagnose shortcut_edge only after first determining that the relevant
       node inventory and required local edge structure are already present.

    10. Do not invent unsupported accident mechanisms, conditions, or events.

    11. Prefer concise, high-value findings. Do not list purely stylistic issues.

    12. First determine whether the current graph has any material diagnosis issue at all.
        Before concluding that no material issue exists, explicitly consider each allowed
        issue_type in this prompt. If no material issue is supported by the evidence after
        those checks, do not force a diagnosis.

[Connectivity expectations]

    1. Hazard consequence nodes should normally be the downstream end of the main causal
       chain.

    2. Avoid diagnosing missing transitive edges as missing direct edges when the existing
       direct local chain is already sufficient.

    3. Except HazardConsequence nodes, every node must have at least one outgoing
       edge.

    4. Every retained Condition node must have both at least one incoming edge
       and at least one outgoing edge. If a Condition is worth retaining under
       CAUSAL_NODE_ISSUE_DEFINITION but lacks a supported downstream
       connection, prefer diagnosing missing_local_link or another edge-level
       issue rather than treating the node as complete in its current form.

    5. If both release and dispersion events are present and supported, check whether the
       graph adequately represents the local release-to-dispersion mechanism.

[Issue definitions]

    [Validation vocabulary references]

    [Node-related definitions]

    1. Use overmerged_node, missing_node, and redundant_node only in ways consistent with
       CAUSAL_NODE_ISSUE_DEFINITION.

    [Edge-related definitions]

    2. Use shortcut_edge, missing_local_link, wrong_relation, and unsupported_edge only in
       ways consistent with CAUSAL_EDGE_ISSUE_DEFINITION.

[Diagnostic decision rules]

    1. If the needed semantics already exist in the current nodes, prefer diagnosing
       missing_local_link or another edge-level issue instead of a node-level issue.

    2. When assessing missing connectivity, do not imply that a direct edge should
       be added if that added edge would create short cut.

    3. For weakly connected retained Condition nodes, prefer diagnosing
       missing_local_link or another edge-level problem over redundant_node when
       a supported downstream connection should exist.

    4. If the current graph already captures the needed local causal meaning, do not
       diagnose a missing_node, redundant_node, or missing_local_link just to make the
       diagnosis more complete.

    5. Do not invent low-value, speculative, or purely completeness-driven issues when the
       graph is already acceptable for the supported evidence.

    6. Do not report multiple issue entries that merely restate the same underlying
       problem. Use the smallest set of issues that captures the material diagnosis problem.

    7. For each issue, keep affected_node_ids and affected_edges as specific and minimal as
       possible. Do not attach broad graph regions when the problem is local.

    8. When multiple issue types could apply, choose the single issue type that best captures
       the primary structural problem with the smallest necessary diagnosis. Prefer the
       issue type that explains the problem most directly and avoids redundant or weaker
       restatements of the same underlying issue.

    9. Prefer diagnosing the root structural problem rather than a downstream symptom. Do not
       diagnose an edge or connectivity problem when the main supported issue is node
       over-merging, node redundancy, schema-level node mismatch, or another more primary
       node-level structural problem.

    10. Do not leave a retained Condition node structurally isolated. If it
        should remain, diagnose the missing supported downstream connection
        rather than accepting the disconnected condition as complete.

    11. If issues_summary is empty, case_assessment.main_problems must also be empty.

    12. If issues_summary is empty, case_assessment.overall_quality must be "good".
        Use "acceptable" only when at least one real but limited issue is present.

[Hazard consequence constraints]

    1. Do not diagnose a missing HazardConsequence node. Treat the hazard consequence
       inventory as fixed by CAUSAL_GRAPH_JSON.

    2. Do not use missing_node, redundant_node, schema_mismatch, or other issue types to
       imply that an additional HazardConsequence node should be added. If the downstream
       consequence representation seems imperfect, diagnose only the existing node labels,
       evidence, or connectivity.

OUTPUT REQUIREMENTS

If no material diagnosis issue is supported:

  - set case_assessment.overall_quality to "good"
  - return an empty issues_summary list

Do not manufacture issues just to avoid returning an empty issues_summary.
Order issues_summary from highest-value finding to lowest-value finding, using severity and
structural importance.

Return one JSON object using the exact `graph_diagnosis`
output structure defined in CAUSAL_ISSUE_OUTPUT_DEFINITION.

OUTPUT FORMAT

Return JSON only.
Do not include explanations or additional text outside the JSON object.
